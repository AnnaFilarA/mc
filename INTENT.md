## 1. Проблема

Поставщики маркетплейса М.Видео присылают карточки товаров с характеристиками в свободной форме. Важные значения спрятаны в описании, записаны по-разному («16GB», «16 Гб», «16 гигов») или отсутствуют в структурированных полях. Такой товар не попадает в фильтры поиска, покупатель его не находит, М.Видео теряет продажи.

Ручная проверка не масштабируется: на маркетплейсе 15 тыс.+ поставщиков, каждый месяц приходит ещё 1,6 тыс., каталог растёт втрое за год.

**Что сказал эксперт на продуктовом чекпоинте (это надо закрыть в финале):**
1. Не хватило перевода результата в бизнес-метрики.
2. Чем процесс отличается от ручной проверки, если человек всё равно контролирует работу?
3. Если человек не контролирует — какова цена ошибки и не будет ли она дороже ручной обработки?

## 2. Результат

### 2.1. Что должно получиться

Каскадный пайплайн и тонкий API поверх него: текст карточки → структурированные характеристики, у каждой есть значение, статус, уверенность и обоснование.

Плюс **веб-интерфейс с выбором роли**: кабинет менеджера по качеству (исключения, решения по полям, утверждение новых категорий) и кабинет продавца (предзаполнение при создании карточки, ответы на вопросы). Подробно — SPEC.md, раздел 4.

Главный принцип: **минимум денег и времени**. Дешёвый этап всегда идёт первым, дорогой включается только для того, что не решил предыдущий.

```
Карточка (title, description, seller_attributes)
  → Шаг 0. Подготовка: очистка текста, определение категории, схема обязательных полей
  → Этап 1. Правила и словари (regex + словари синонимов)              ← всегда
  → Этап 2. Лёгкие ML-модели                                           ← только поля без уверенного ответа
  → Этап 3. LLM (подключаемый, по умолчанию выключен)                  ← только спорные поля, в пределах бюджета
  → После каждого этапа: нормализация → проверка «значение есть в тексте» → уверенность
  → Статус по каждому полю и итог по карточке
```

### 2.2. Контракт ответа (на каждую характеристику)

| Поле | Значение |
|---|---|
| `attribute` | код атрибута, например `ram` |
| `was` | исходное значение от поставщика (или `null`) |
| `value` | найденное или нормализованное значение в каноническом виде |
| `unit` | единица, если есть |
| `status` | `unchanged` / `proposed` / `low_confidence` / `conflict` / `missing` |
| `confidence` | 0..1, калиброванная |
| `stage` | `rules` / `ml` / `llm` |
| `evidence` | подтверждающий фрагмент текста и позиция `[start, end]` |
| `question_to_seller` | текст вопроса с вариантами, если статус `conflict` или `missing` |

Статусы:
- **`unchanged`** — значение поставщика верное и уже в каноническом виде.
- **`proposed`** — модуль нашёл или нормализовал значение с уверенностью выше порога; принимающая система может применить его автоматически.
- **`low_confidence`** — кандидат есть, но уверенность ниже порога; показать менеджеру.
- **`conflict`** — источники противоречат друг другу (атрибут ≠ описание); спросить поставщика.
- **`missing`** — значения нет в тексте; спросить поставщика.

Правило без исключений: **значение без `evidence` не может получить статус `proposed`**. Так мы не выдумываем характеристики.

## 3. Кого касается

| Кто | Роль | Что получает |
|---|---|---|
| Бизнес М.Видео | заказчик | больше товаров в фильтрах → выше CTR, конверсия, GMV |
| Менеджер по качеству карточек | пользователь | видит только исключения: `low_confidence`, `conflict`, новые значения |
| Поставщик | пользователь | конкретный вопрос с вариантами вместо отклонения карточки |
| Покупатель | выгодоприобретатель | полные фильтры, товар соответствует описанию |
| Принимающие системы М.Видео | потребитель API | статусы, по которым они сами решают: применить, показать менеджеру, спросить поставщика |

**Граница ответственности модуля:** обработать карточку и выдать объяснимый результат. Публикация, связь с поставщиком и работа менеджеров остаются в системах М.Видео.

## 4. Как появляются новые товары и новые категории

### 4.1. Новые и изменённые товары
- **Онлайн:** при загрузке или изменении карточки система М.Видео вызывает `POST /v1/extract`. Ответ за < 1 с без LLM.
- **Ночной прогон:** раз в сутки пакетно перепроверяем только изменившиеся карточки. Изменение определяем по хэшу `title + description + seller_attributes`. Ответ идемпотентен по `product_id` + хэш.
- Неизменённые карточки повторно не обрабатываются, это экономия.

### 4.2. Новая категория (ИИ предлагает, менеджер утверждает)
1. Пришла карточка, категория которой не найдена в `config/categories/` (или классификатор категории не уверен).
2. Карточка получает статус `missing` по всем полям и попадает в очередь «новая категория». Публикация не блокируется, решение за системой М.Видео.
3. Когда в очереди накопилось N карточек категории (по умолчанию 20), `schema_bootstrap.py` один раз вызывает LLM. Она по этим карточкам и, если есть, по статистике поисковых запросов предлагает черновик схемы: список обязательных полей, типы (число + единица / перечисление / текст), допустимые значения.
4. Черновик сохраняется как `config/categories/<new>.draft.yaml`.
5. **Менеджер один раз утверждает схему**: правит и переименовывает в `.yaml`. Это единственная ручная операция на категорию.
6. Из утверждённой схемы автоматически собираются словари и шаблоны Этапа 1. С этого момента категория обрабатывается дёшево.
7. Когда накопится размеченных примеров (ответы поставщиков и менеджеров), включается Этап 2 для этой категории.

### 4.3. Петля обратной связи
Ответы поставщиков и решения менеджеров сохраняются как разметка (`data/feedback/`). Новые синонимы пополняют словари Этапа 1, накопленные примеры используются при переобучении Этапа 2. Доля обращений к LLM со временем падает.

## 5. Ответ эксперту: чем это лучше ручной проверки и сколько стоит ошибка

### 5.1. Человек контролирует не всё
- Значения со статусом `proposed` и уверенностью выше порога применяются **без человека**.
- Человек видит только `low_confidence` и `conflict`. Цель: не больше 30% полей.
- Контроль качества автоматических решений — **выборочный аудит 1–2%** принятых значений. Он показывает фактическую точность и позволяет поднять порог, если точность падает.

Разница с ручной проверкой: менеджер работает со списком исключений, а не со всем каталогом.

### 5.2. Цена ошибки
Основная цена ошибки — **товар попадает не в тот фильтр** (или не попадает в нужный) и не продаётся.

Порог уверенности выбираем не «на глаз», а минимизируя общую стоимость:

```
Стоимость(порог) = доля_полей_человеку(порог) × цена_ручной_проверки_поля
                 + доля_ошибок_в_авто(порог)  × цена_ошибки_поля
```

- `цена_ручной_проверки_поля` ≈ 765 ₽/ч ÷ 60 × минут на поле (оценка команды: зарплата 97 тыс. ₽ + взносы).
- `цена_ошибки_поля` оцениваем через данные кликов: сколько показов и кликов получает товар из фильтра по этому атрибуту × конверсия × средний чек × доля маржи. Если данных не хватает, задаём сценарии (низкая / средняя / высокая) и показываем, что порог устойчив.
- Строим график «порог → стоимость» по каждому атрибуту. Это и есть ответ на вопрос эксперта.

### 5.3. Бизнес-метрики (чего не хватило на чекпоинте)
Считаем на датасете кейса (клики по запросам):
- **Покрытие фильтров, взвешенное по трафику:** доля кликов и запросов по атрибутам, где у товара после обработки есть значение, было → стало.
- **Доп. товаров в выдаче:** сколько карточек начинают попадать в выдачу по популярным фильтрам.
- **Оценка эффекта на GMV:** доп. показы × CTR × конверсия × средний чек. Подаём как сценарную оценку, а не как обещание.
- **Экономия времени:** часы менеджеров до и после при фактической доле `low_confidence + conflict`.

## 6. Метрики качества

Требование кейса — считать **по каждому атрибуту**, а не общую accuracy.

| Метрика | Цель MVP |
|---|---|
| Precision по полям со статусом `proposed` | ≥ 0,90 |
| Recall / F1 по каждому атрибуту | отчёт по всем; F1 ≥ 0,80 на ключевых |
| Coverage (доля карточек с заполненным атрибутом), было → стало | рост |
| F1 с весом по трафику фильтров | отчёт |
| Метрики отдельно по каждой из топ-5 категорий | разброс ≤ 10 п.п. |
| Доля полей, дошедших до LLM | ≤ 20% |
| Время на карточку без LLM (p95) | < 1 с |
| Значения без `evidence` среди `proposed` | 0 |

Обязательное сравнение конфигураций на одной тестовой выборке:
1. Только правила.
2. Правила + ML.
3. Правила + ML + LLM (если LLM доступна).

Для каждой: F1 по атрибутам, coverage, время, стоимость на 1 000 карточек.

Разбиение данных: train ~70% / validation ~15% / test ~15%. Карточки одного товара от разных поставщиков — в одну часть. Стратификация по категориям. На test ничего не настраиваем.

## 7. Ограничения

- **Только текст:** title, description, seller_attributes. Фото не используем.
- **Не выдумывать:** `proposed` только с подтверждающим фрагментом текста и только из справочника для перечислимых атрибутов.
- **Минимум затрат:**
  - LLM по умолчанию выключена.
  - Если включена — только для полей без уверенного ответа после Этапов 1–2, только релевантный фрагмент текста, строгая JSON-схема ответа, лимит вызовов на прогон, кэш ответов.
  - Нет бюджета — поле получает `low_confidence` без вызова LLM.
- **Железо:** Google Colab, бесплатный уровень. Этап 2 — только лёгкие модели, которые обучаются на CPU за минуты:
  - TF-IDF + логистическая регрессия для перечислимых атрибутов и категории;
  - градиентный бустинг (CatBoost/LightGBM) для ранжирования кандидатов из регулярок, например «16 ГБ — это ОЗУ или накопитель».
  - Тяжёлые трансформеры не используем, если не доказано, что они нужны.
- **Срок:** 1–2 дня. Сначала рабочий сквозной пайплайн на правилах и честные метрики, потом улучшения.
- **Объём MVP:** топ-5 категорий датасета по числу карточек (определяет EDA). Остальные категории проходят через Этап 1 с общими правилами (бренд, цвет, память) и маршрут «новая категория».
- **Воспроизводимость:** запуск по README в Colab одной командой: `python -m src.pipeline --input <file> --output outputs/`.
- **Язык:** комментарии и README на русском, код и имена — на английском.

## 9. Порядок работы (1–2 дня)

1. **Данные (первые 1–2 часа).** Скачать ZIP, положить на Google Drive, примонтировать в Colab. Если ссылка не скачивается — сразу писать организаторам.
2. **EDA.** Поля, форматы, пропуски, доля размеченных карточек, топ-5 категорий, список обязательных полей, распределение значений, длинный хвост. Сохранить выводы в `outputs/metrics/eda_summary.md`.
3. **Схемы категорий** в `config/categories/*.yaml` по EDA и перечню обязательных полей из датасета.
4. **Этап 1 + нормализация + evidence + статусы.** Сквозной прогон, первый `predictions.jsonl`, метрики конфигурации «только правила». **Это минимальный сдаваемый результат — довести до него в первый день.**
5. **Этап 2** для атрибутов, где правила дают низкий recall. Метрики «правила + ML».
6. **Этап 3** — интерфейс и заглушка; при наличии ключа — реальный вызов на спорных полях валидации. Метрики «полный каскад».
7. **Калибровка порогов** на validation по формуле стоимости из раздела 5.2.
8. **Бизнес-метрики** по кликам (раздел 5.3).
9. **API** (`src/api.py`, FastAPI): `POST /v1/extract` возвращает контракт из 2.2.
10. **README, итоговые таблицы метрик, презентация.**
