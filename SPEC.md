# SPEC.md — AttrGuard: спецификация

> INTENT.md отвечает на вопрос **«зачем и что»**. Этот файл отвечает на вопрос **«как именно»**: требования, дизайн, интерфейсы, порядок работ, правила для агентов.
> Если документы противоречат друг другу — см. раздел 1.

---

## 1. Как читать намерения

### 1.1. Иерархия документов
При противоречии побеждает документ выше по списку:

1. **Прямое указание человека в текущей сессии.**
2. **INTENT.md** — цель, границы, ограничения. Это «конституция» проекта.
3. **SPEC.md** (этот файл) — как реализуем.
4. **Текст кейса М.Видео** — требования заказчика. Если SPEC ему противоречит, это ошибка SPEC: сообщи человеку.
5. **DECISIONS.md** — журнал уже принятых решений.
6. Здравый смысл агента.

### 1.2. Как понимать формулировки
- **ДОЛЖНО** — обязательное требование. Без него задача не принимается.
- **СЛЕДУЕТ** — делаем, если это не ломает сроки. Если не сделали, запиши причину в DECISIONS.md.
- **МОЖНО** — по желанию, только когда всё обязательное готово.
- Если требование неоднозначно, исходи из его цели (раздел «зачем» в INTENT.md) и выбирай **самый дешёвый и быстрый вариант, который эту цель достигает**.
- Не добавляй функции, которых нет ни в INTENT, ни в SPEC. Хорошая идея → запиши в `BACKLOG.md`, но не делай.

### 1.3. Три вопроса перед любым решением
1. Это приближает нас к сдаваемому результату за 1–2 дня?
2. Это самый дешёвый способ (по деньгам и по времени)?
3. Это не нарушает правило «нет значения без подтверждения в тексте»?

Если хотя бы один ответ «нет» — остановись и выбери другой вариант.

## 2. Требования

### 2.1. Функциональные требования

| ID | Требование | Уровень |
|---|---|---|
| F1 | Пайплайн принимает карточку (`product_id`, `title`, `description`, `seller_attributes`, опц. `category_hint`) и возвращает ответ по контракту 3.3 | ДОЛЖНО |
| F2 | Шаг 0 определяет категорию (из `category_hint`, иначе классификатор по `title`) и загружает её схему из `config/categories/` | ДОЛЖНО |
| F3 | Этап 1 (правила + словари) извлекает кандидатов для всех атрибутов схемы | ДОЛЖНО |
| F4 | Нормализатор приводит значения к каноническому виду (единицы, синонимы, справочник) | ДОЛЖНО |
| F5 | Проверка evidence: у значения со статусом `proposed` есть фрагмент исходного текста с позицией | ДОЛЖНО |
| F6 | Уверенность 0..1 у каждого значения, пороги по атрибутам из `config/thresholds.yaml` | ДОЛЖНО |
| F7 | Пять статусов: `unchanged`, `proposed`, `low_confidence`, `conflict`, `missing` | ДОЛЖНО |
| F8 | Этап 2 (лёгкие ML-модели) вызывается только для полей без уверенного ответа после Этапа 1 | ДОЛЖНО |
| F9 | Этап 3 (LLM) — подключаемый интерфейс; по умолчанию выключен; лимит вызовов и кэш | ДОЛЖНО (интерфейс), СЛЕДУЕТ (реальный вызов) |
| F10 | Для `conflict` и `missing` формируется `question_to_seller` с вариантами ответа | ДОЛЖНО |
| F11 | Пакетный режим: `python -m src.pipeline --input X --output outputs/` → `predictions.jsonl` и `predictions.csv` | ДОЛЖНО |
| F12 | API `POST /v1/extract` (одна карточка) и `POST /v1/extract/batch` | ДОЛЖНО |
| F13 | Веб-интерфейс с выбором роли: **кабинет менеджера** и **кабинет продавца** (раздел 4) | ДОЛЖНО |
| F14 | Ответы продавца и решения менеджера сохраняются как разметка в `data/feedback/` | ДОЛЖНО |
| F15 | Новая категория: очередь → черновик схемы от LLM → утверждение менеджером в веб-интерфейсе | СЛЕДУЕТ |
| F16 | Идемпотентность: повторный вызов с тем же `product_id` и хэшем текста берёт результат из кэша | СЛЕДУЕТ |
| F17 | Ночной пакетный прогон только изменившихся карточек (скрипт + описание в README) | МОЖНО |

### 2.2. Нефункциональные требования

| ID | Требование |
|---|---|
| N1 | Работает в Google Colab (бесплатный уровень) и локально на Python 3.10+ |
| N2 | Без LLM: p95 < 1 с на карточку; пакет 10 тыс. карточек < 15 мин на CPU |
| N3 | Этап 2 обучается на CPU за минуты; тяжёлые трансформеры запрещены, пока не доказано, что без них нельзя |
| N4 | Стоимость LLM: ≤ 20% полей доходят до Этапа 3; лимит вызовов на прогон задаётся в конфиге |
| N5 | Воспроизводимость: фиксированный `random_state`, версии в `requirements.txt`, запуск по README |
| N6 | Тесты: `pytest` на эталонных примерах (`tests/fixtures/*.json`), должны проходить перед каждым слиянием |
| N7 | Код и имена на английском; README, комментарии к бизнес-логике и UI — на русском |
| N8 | Никаких секретов в коде: ключ LLM только из переменной окружения `LLM_API_KEY` |

### 2.3. Метрики приёмки
Из INTENT.md, раздел 6. Считаются скриптом `src/evaluate.py`, результаты в `outputs/metrics/`:
- `per_attribute.csv` — precision, recall, F1, coverage до/после по каждому атрибуту и категории;
- `configs_comparison.csv` — «правила» / «правила + ML» / «полный каскад»: F1, coverage, время, стоимость на 1 000 карточек, доля LLM;
- `threshold_cost.csv` и график — стоимость в зависимости от порога (ответ эксперту);
- `business.md` — бизнес-метрики по кликам.

## 3. Дизайн системы

### 3.1. Компоненты

```
┌──────────────── Веб (FastAPI + Jinja2 + HTMX) ────────────────┐
│  /            выбор роли                                       │
│  /manager     кабинет менеджера   /seller   кабинет продавца   │
└───────────────┬───────────────────────────────────────────────┘
                │ вызывает
┌───────────────▼──────────────── API ──────────────────────────┐
│  POST /v1/extract   POST /v1/extract/batch   POST /v1/feedback │
│  GET  /v1/queue     POST /v1/categories/{id}/approve           │
└───────────────┬───────────────────────────────────────────────┘
                │
┌───────────────▼──────────── Ядро (src/) ──────────────────────┐
│ prepare → rules → [ml] → [llm] ; после каждого: normalize+check│

└───────────────┬───────────────────────────────────────────────┘
                │
```

Хранилище для MVP: файлы JSON/JSONL и SQLite (`data/attrguard.db`). Никаких внешних БД.

### 3.2. Модули и их ответственность

### 3.3. Контракт (src/contracts.py)

```python
class Status(str, Enum):
    unchanged = "unchanged"; proposed = "proposed"
    low_confidence = "low_confidence"; conflict = "conflict"; missing = "missing"

class Evidence(BaseModel):
    text: str; start: int; end: int; source: Literal["title","description","seller_attributes"]

class AttributeResult(BaseModel):
    attribute: str; was: str | None; value: str | None; unit: str | None
    status: Status; confidence: float; stage: Literal["rules","ml","llm","none"]
    evidence: Evidence | None; question_to_seller: dict | None   # {"text": str, "options": [str]}

class ExtractResponse(BaseModel):
    product_id: str; category: str; category_confidence: float
    attributes: list[AttributeResult]; card_status: Literal["ready","needs_manager","needs_seller"]
    llm_calls: int; elapsed_ms: int; text_hash: str
```

**Контракт меняет только оркестратор.** Подагент, которому нужно изменение, пишет запрос в `DECISIONS.md` и останавливается на этом месте.

### 3.4. Логика статусов (cascade.py)
1. Нет ни одного кандидата с evidence → `missing`.
2. Кандидаты из разных источников дают разные канонические значения и оба уверенные (> порога «низкий») → `conflict`.
3. Лучший кандидат ≥ порога атрибута:
   - совпадает с `was` → `unchanged`;
   - иначе → `proposed`.
4. Иначе → `low_confidence`.

`card_status`: все обязательные `unchanged`/`proposed` → `ready`; есть `conflict`/`missing` → `needs_seller`; иначе → `needs_manager`.

### 3.5. Этапы
- **Этап 1.** Словари из EDA (бренды, модели процессоров, цвета + синонимы) и регулярки для «число + единица». Каждое правило возвращает span. Уверенность: точное совпадение со словарём 0,95; регулярка 0,85; нечёткое совпадение 0,6. Потом калибруется.
- **Этап 2.**
  - Перечислимые атрибуты: TF-IDF (символьные n-граммы) + логистическая регрессия.
  - Числовые с конфликтом единиц (ОЗУ против накопителя): CatBoost-ранжирование кандидатов из регулярок по признакам контекста (слова рядом, позиция, величина).
  - Калибровка — isotonic/Platt на validation.
- **Этап 3.** Промпт содержит только спорные атрибуты, их допустимые значения и релевантные куски текста (±200 символов вокруг кандидатов). Ответ — строгий JSON. Значение без цитаты, найденной в тексте, отбрасывается. Пометка `stage="llm"`; статус максимум `low_confidence`, если в конфиге не включено иное.

## 4. Веб-интерфейс (дизайн)

Стек: **FastAPI + Jinja2 + HTMX + один CSS-файл**. Без сборки фронтенда, без React — так дешевле и быстрее. Запуск: `uvicorn src.api:app`. Для демо из Colab — туннель `cloudflared`. Для постоянного адреса — Hugging Face Spaces (Docker, бесплатно).

### 4.1. Общие правила
- Стиль презентации: белый фон, акцент красный `#E30611`, тёмный `#15171A`, шрифт Inter / системный sans.
- Текст не мельче 14 px, статусы цветом и словом (не только цветом):
  - `proposed` — зелёный;
  - `low_confidence` — жёлтый;
  - `conflict` / `missing` — красный;
  - `unchanged` — серый.
- Демо-данные: 30–50 карточек из test-части, загружаются при старте.

### 4.2. `/` — выбор роли
Две большие карточки: «Я менеджер по качеству» и «Я продавец». Выбор хранится в cookie, переключатель роли — в шапке на всех страницах.

### 4.3. Кабинет менеджера `/manager`
- **Сводка:** проверено, исправлено автоматически, ждут менеджера, ждут продавца, доля LLM.
- **Таблица исключений:** только карточки со статусом `needs_manager` или `needs_seller`. Колонки: товар, категория, проблемные поля (чипы), мин. уверенность, статус запроса продавцу (отправлен / прочитан / ответ получен + дата).
- **Карточка товара `/manager/card/{id}`:**
  - слева — исходный текст с подсветкой evidence;
  - справа — таблица «атрибут · было · предложено · статус · уверенность · этап · источник»;
  - действия по полю: «Принять», «Исправить», «Отправить вопрос продавцу». Каждое действие → `POST /v1/feedback`.
- **Очередь новых категорий `/manager/categories`:** черновик схемы, кнопки «Утвердить» и «Править».

### 4.4. Кабинет продавца `/seller`
- **Мои товары:** список с бейджем «нужно уточнить N полей».
- **Создание или правка карточки `/seller/new`:**
  - поля «Название», «Описание», «Характеристики»;
  - кнопка «Проверить» (или проверка при вводе с задержкой 1 с) → вызывает `/v1/extract`;
  - ниже — обязательные поля категории с предзаполнением, варианты из справочника, подсказка формата для ручного ввода, индикатор «попадёт в N из M фильтров».
- **Вопросы от каталога `/seller/questions`:** вопрос с кнопками-вариантами; ответ → `POST /v1/feedback` → карточка пересчитывается.

### 4.5. Критерии приёмки UI
- Сценарий 1: продавец вводит карточку → видит предзаполнение и вопросы → отвечает → менеджер видит, что ответ получен.
- Сценарий 2: менеджер открывает спорную карточку → принимает или исправляет поле → карточка уходит из списка исключений.
- Оба сценария показываются на демо за 2 минуты без ошибок в консоли.

## 6. Модели: какую нейросеть где использовать

### 6.1. Для разработки (агенты)

| Роль | Модель | Почему |
|---|---|---|
| Оркестратор: план, контракт, ревью, интеграция, спорные решения | **Claude Opus** (самый сильный уровень) | ошибки в архитектуре и контракте дорого исправлять |
| Подагенты, которые пишут код модулей, тесты, UI | **Claude Sonnet** (средний уровень) | хороший код при меньшей стоимости и большей скорости |
| Массовые простые задачи: синонимы для словарей, разбор 1 000 примеров, генерация фикстур | **Claude Haiku** (быстрый и дешёвый) | много однотипной работы |

### 6.2. Внутри продукта (Этап 3)
Нужна самая дешёвая модель, которая умеет строгий JSON и понимает русский:
- **GigaChat Lite** или **YandexGPT Lite** через API — основной вариант для российского заказчика;
- **Qwen2.5-7B-Instruct** локально в Colab на GPU — если ключа нет (бесплатно, медленнее);
- для черновика схемы новой категории (редкий вызов) можно модель уровнем выше: GigaChat Pro или YandexGPT Pro.

Модель задаётся в `config/llm.yaml`; код не зависит от провайдера.

## 7. Скиллы: какие и как применять

Скилл — сохранённая инструкция для повторяющейся процедуры (`.claude/skills/<name>/SKILL.md`). Создаём в фазе 0, используем все потоки.

| Скилл | Когда применять | Что внутри |
|---|---|---|
| `add-category` | появилась новая категория или утверждён черновик | шаги: схема YAML → словари → регулярки → фикстуры → тест → запись в DECISIONS |
| `run-eval` | после любого изменения в rules/ml/llm/cascade | команда прогона, какие файлы обновить, как сравнить с прошлым запуском, порог «стало хуже» |
| `add-rule` | нужно добавить правило/синоним | формат правила, обязательный span, тест на 3 позитивных и 2 негативных примера |
| `ui-screen` | новый экран веб-интерфейса | шаблон Jinja, цвета и статусы из 4.1, проверка в браузере |
| `log-decision` | любое решение, которого нет в INTENT/SPEC | формат записи в DECISIONS.md |

Встроенные скиллы:
- **pptx** — финальная презентация из `outputs/metrics/`;
- **xlsx** — таблицы метрик для жюри, если нужен Excel;
- **pdf** — экспорт презентации.

## 8. Спорные моменты: как отрабатывать

### 8.1. Кто решает

| Ситуация | Кто решает | Как |
|---|---|---|
| Неоднозначность в задаче модуля | подагент | выбирает самый дешёвый вариант, пишет в DECISIONS.md, продолжает |
| Нужно изменить контракт или общий конфиг | оркестратор | подагент останавливается, пишет запрос в DECISIONS.md; оркестратор решает и уведомляет все потоки |
| Два потока трогают один файл | оркестратор | у каждого файла один владелец (таблица 3.2); чужие файлы — только через запрос |
| Метрика ухудшилась после изменения | автор изменения | откатить или доказать, что стало лучше по F1 с весом трафика; сравнение в `run-eval` |
| Правило и ML дают разные значения | код (cascade) | статус `conflict` или выбор по калиброванной уверенности; не «угадывать» |
| Значение нашла только LLM, без цитаты | код | отбросить. Без исключений |
| Нужны деньги (платный API), удаление данных, публикация наружу, изменение test-выборки | **человек** | агент останавливается и спрашивает |
| Утечка test в обучение или подбор порогов | **человек** | агент сообщает немедленно |

### 8.2. Формат записи в DECISIONS.md
```
## 2026-10-16 14:20 · поток B · rules.py
Вопрос: как писать «8/256GB» — ОЗУ/память или только память?
Решение: первое число → ram, второе → storage, если категория = smartphones.
Почему: так в 90% карточек EDA; дешевле, чем ML.
Обратимо: да (правило в rules/smartphones.yaml).
```

### 8.3. Когда остановиться и спросить человека
- Решение необратимо или стоит денег.
