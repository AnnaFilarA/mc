## 2026-10-16 21:00 · оркестратор · канон значений
Вопрос: как выглядит каноническое значение.
Решение: number — строка числа без единицы, точка как разделитель (`"8"`, `"6.67"`), 1 ТБ = `"1024"` GB; единица в `unit` (`GB`, `inch`, `Hz`).
enum — строго из `values` схемы (цвета по-русски с заглавной, `ё→е`).
`unchanged` — если `was` после `strip()`/без учёта регистра равен `value` или `"value unit"` и подтверждён;
значение продавца верное, но в другом виде («8 Гб») → `proposed` (нормализовано).
Почему: простое и проверяемое правило «уже в каноническом виде» (INTENT 2.2).
Обратимо: да.

## 2026-10-16 22:00 · поток E · src/llm.py
Вопрос: как устроен Этап 3 и какие провайдеры поддержаны.
Решение: `HttpLLM` с адаптерами провайдеров (`openai_compatible`, `gigachat` — тот же формат, `yandexgpt` — нативный API); транспорт инъецируется (`transport(url, headers, payload, timeout) -> dict`), по умолчанию httpx. Статус `low_confidence` обеспечивает порог proposed 0.80 > 0.7; поле `max_status` в конфиге документирует правило, применяет его каскад (поток B) — поток B не должен поднимать score кандидатов stage=llm выше порога proposed.
Почему: код не зависит от провайдера (SPEC 6.2), тесты без сети, значение без цитаты в тексте отбрасывается (SPEC 8.1).
Обратимо: да (`config/llm.yaml`, `_ADAPTERS` в `src/llm.py`).

## 2026-10-16 22:00 · поток D · evaluate.py — определения метрик
Вопрос: что считать TP/FP/FN и как сравнивать значения.
Решение: единица — пара (карточка, атрибут из эталона). Авто-значение = статус `unchanged`/`proposed` и непустой `value`. TP — авто-значение совпало с эталоном; FP — авто-значение неверно или эталон null; FN — эталон есть, а авто-значения нет или оно неверно (неверное = и FP, и FN). Канон сравнения: strip, lower, ё→е, схлопнутые пробелы, числа как float (`"6,60"` = `"6.6"`), единица не сравнивается. `precision_proposed` — только по `proposed`. Пустой знаменатель → пустая ячейка (NaN); F1 = 2TP/(2TP+FP+FN). macro F1 — среднее по парам (категория, атрибут); micro — по суммарным TP/FP/FN. Полное описание — в docstring `src/evaluate.py`.
Почему: единственное определение, при котором «неуверенное, но верное» поле (low_confidence) честно штрафуется в recall, а «уверенная ошибка» — в precision.
Обратимо: да (`src/evaluate.py`, функция `row_metrics`).

## 2026-10-16 22:00 · поток D · evaluate.py — gold из фикстур, неизвестные карточки
Вопрос: как читать эталон фикстур и что делать с несовпадающими наборами карточек/атрибутов.
Решение: `value` есть → эталон; нет `value` и статус `missing` → эталон null; нет `value` и `conflict` (или иной статус) → пара исключена из P/R (`n_excluded`), но участвует в coverage и долях статусов. Атрибуты, которых нет в эталоне, игнорируются (счётчик `pred_attributes_not_in_gold` в summary); карточка эталона без предсказания → все её поля «missing» (FN при эталоне не-null), счётчик `cards_without_prediction`.
Почему: эталон определяет, что оцениваем; пропавшая карточка не должна улучшать метрики.
Обратимо: да.

## 2026-10-16 22:00 · поток D · evaluate.py — стоимость порога
Вопрос: как симулировать порог t по готовым предсказаниям.
Решение: доли считаются от всех оценённых полей (кроме исключённых). К человеку уходит поле без кандидата (conflict, missing, low_confidence без value) или с confidence < t; кандидат `low_confidence` с непустым `value` считается кандидатом (это позволяет оценить пороги ниже боевого). Ошибка в авто — кандидат с confidence ≥ t, не равный эталону (или эталон null). Цена ручной = rate/60 × minutes_per_field (config/thresholds.yaml → cost) = 6.375 ₽; цена ошибки — сценарии low/mid/high оттуда же. Кривые строятся по атрибуту (по всем категориям вместе — как ключи `attributes:` в thresholds.yaml) и итог (`ALL`). При равной стоимости `best_thresholds` берёт более строгий (больший) порог. Порог t сравнивается с confidence как `confidence ≥ t`.
Почему: порог в конфиге задан по коду атрибута, без категории; при плоском участке кривой безопаснее больший порог.
Обратимо: да. Замечание поток G: калибровать только на validation; на малых выборках оптимум шумный.

## 2026-10-16 22:00 · поток D · evaluate.py — сравнение конфигураций, веса, разброс
Вопрос: как организовать configs_comparison, веса трафика и разброс по категориям.
Решение: CLI `--compare rules=… rules_ml=… full=…`; отсутствующие/несуществующие файлы → строка со статусом «не запускалась». ## 2026-10-16 21:10 · поток B · rules.py (ОЗУ/накопитель)
Вопрос: как читать «8/256GB», «16 ГБ + 512 ГБ», одиночное «128 ГБ», «8 ГБ 512 ГБ SSD»; что не считать памятью.
Решение: пара «A/B» или «A+B» с единицей у второго числа: первое → ram, второе → storage (для всех категорий, не только смартфонов), если A ≤ 64, B ≥ 16 ГБ и A < B; score 0.88.
Число с подписью (ОЗУ/RAM/DDR/«оперативная память» ↔ SSD/HDD/«встроенная память»/«памяти») слева или справа — 0.88. Два числа подряд без подписей: меньшее → ram, большее → storage (0.82). Одиночное без подписи: ≥128 ГБ → storage 0.82; 32/64 → storage 0.7; ≤24 → ram 0.65 (ниже порога, low_confidence).
Не память: рядом RTX/GTX/Radeon/«видеокарта»/GDDR/VRAM, microSD/SD/«карт памяти»/«слот»/«расширение»/кэш. «5G» и даты «12/05/2024» не считаются.
Почему: покрывает все трудные фикстуры без ML; консервативно там, где подписи нет.
Обратимо: да (src/rules.py, `_memory`).

## 2026-10-16 21:10 · поток B · normalize.py
Вопрос: что нормализует `normalize`, если этап уже выставил `value`.
Решение: источник — `candidate.value`, если задан (словарные правила кладут туда канон, ML/LLM могут положить свой), иначе `raw_value`; в любом случае значение проверяется по `values`/`range` схемы, иначе `value=None`. number: ТБ→×1024, МБ→/1024, см→дюймы (1 знак), запятая → точка, unit из схемы; чужая единица («ГБ» для inch) → None. enum: сравнение без регистра и ё→е с `values`, затем через словарь.

## 2026-10-16 21:10 · поток B · cascade.py (статусы)
Вопрос: детали SPEC 3.4.
Решение:
- Уверенность значения = 1 − Π(1 − лучший score по каждому источнику), максимум 0.99: подтверждение из второго источника повышает уверенность.
- conflict: два разных канона, есть пара кандидатов из РАЗНЫХ источников, оба score > low. По указанию оркестратора у conflict и low_confidence заполнены value/unit/confidence/evidence лидирующего значения; `question_to_seller.options` — конфликтующие значения с единицей («8 GB», «16 GB»), text называет источники («в описании — …; в характеристиках продавца — …»).
- missing: value=None, stage="none", confidence=0; options — `values` схемы (с единицей) или [] для атрибутов только с range; если у продавца есть нераспознанное значение, оно названо в тексте вопроса.
- unchanged: `was` == value или «value unit» (strip, без регистра; ё не склеиваем); значение продавца, подтверждённое только полем продавца, тоже unchanged (evidence — в seller_attributes); в другой форме («8 Гб») → proposed.
- Этап 2 вызывается для missing/low_confidence/conflict, принимаются только кандидаты по этим атрибутам; Этап 3 — для conflict/low_confidence, результат LLM всегда low_confidence (conf ≤ high−0.01), stage="llm", бывший conflict после LLM перестаёт быть conflict (его решает менеджер).
- `llm_calls` — число вызовов `llm.calls` за эту карточку (разница до/после), а не накопленное за прогон.
- Пороги: `attributes.<код>` или `attributes.<категория>.<код>` в thresholds.yaml; схемы и пороги перечитываются при изменении файла (mtime), перезапуск не нужен.
Почему: детерминированно, проверяемо, без «угадывания».
Обратимо: да.
