## 2026-10-16 21:00 · оркестратор · src/contracts.py
Вопрос: SPEC 3.3 не описывает входную карточку и формат обмена между этапами.
Решение: `Card(product_id, title, description, seller_attributes: dict[str,str], category_hint)`; `Candidate(attribute, raw_value, value, unit, score, stage, evidence)`.
Evidence для `seller_attributes` указывает на строку `seller_attributes_text()` — «ключ: значение» через `\n`.
Инвариант `evidence_is_valid()`: `source_texts(card)[source][start:end] == text` (по сырому тексту, не очищенному).
Почему: нужен единый проверяемый способ доказать, что значение есть в тексте.
Обратимо: да (меняет только оркестратор).

## 2026-10-16 21:00 · оркестратор · канон значений
Вопрос: как выглядит каноническое значение.
Решение: number — строка числа без единицы, точка как разделитель (`"8"`, `"6.67"`), 1 ТБ = `"1024"` GB; единица в `unit` (`GB`, `inch`, `Hz`).
enum — строго из `values` схемы (цвета по-русски с заглавной, `ё→е`).
`unchanged` — если `was` после `strip()`/без учёта регистра равен `value` или `"value unit"` и подтверждён;
значение продавца верное, но в другом виде («8 Гб») → `proposed` (нормализовано).
Почему: простое и проверяемое правило «уже в каноническом виде» (INTENT 2.2).
Обратимо: да.

## 2026-10-16 21:00 · оркестратор · cascade / card_status
Вопрос: SPEC 3.4 — `card_status` считается по всем атрибутам или по обязательным?
Решение: по обязательным (`required: true`); необязательные поля статус карточки не меняют, но в ответе есть.
Почему: иначе любая карточка без, например, частоты обновления ТВ уходит продавцу — лишняя нагрузка.
Обратимо: да.

Почему: совмещает оба пункта и даёт продавцу хоть какой-то результат.
Обратимо: да.

## 2026-10-16 22:00 · поток C · src/api.py (ядро и фоллбек)
Вопрос: ядро (`src.cascade.extract`) ещё бросает NotImplementedError.
Решение: `Ctx.run_core` вызывает ядро; на NotImplementedError срабатывает единственная функция `Ctx.fallback_extract`: для карточек фикстур (совпали product_id и title/description) значения и статусы из `expected`, `proposed`/`unchanged` понижены до `low_confidence` (evidence=None, уверенность 0.6); `conflict`/`missing` получают `question_to_seller` с вариантами из схемы; для произвольной карточки категория по `category_hint` или ключевым словам схем (иначе `unknown` + `_common`), все поля схемы `missing`. В подвале веба при фоллбеке показывается пометка «демо-режим».
Почему: веб и API работают независимо от потока B; после слияния фоллбек не срабатывает (ядро не бросает NotImplementedError).
Обратимо: да (удалить `fallback_extract`).

## 2026-10-16 22:00 · поток C · src/api.py, src/storage.py (идемпотентность, разметка)
Вопрос: что именно считать ключом кэша и куда писать решения (F14, F16).
Решение: ключ кэша `(product_id, sha256(title, description, seller_attributes)[:16])` считается в API до вызова ядра (не зависит от `ExtractResponse.text_hash` ядра); кэш и карточки — в SQLite (`ATTRGUARD_DB`, по умолчанию `data/attrguard.db`). Feedback пишется в таблицу `feedback` и дописывается в `data/feedback/feedback.jsonl` (`ATTRGUARD_FEEDBACK`) вместе с `was`, `proposed_value`, `proposed_status`, `category`, `text_hash` — для разметки. Демо-карточки: `ATTRGUARD_DEMO` (каталог json-фикстур/карточек или .jsonl; по умолчанию `tests/fixtures`); схемы категорий: `ATTRGUARD_CATEGORIES`.
Почему: простое и проверяемое правило; разметка сразу пригодна для обучения/оценки.
Обратимо: да.

## 2026-10-16 22:00 · поток C · src/api.py (решённые поля и статусы карточки)
Вопрос: как «решённое» поле влияет на статусы, если контракт не имеет такого статуса.
Решение: контракт не менялся. Итоговое состояние считается на стороне веба поверх ответа ядра и истории feedback: `accept` берёт предложенное значение; `fix` / `seller_answer` — значение человека; поле становится `unchanged` (если совпало с `was`) или `proposed`, уверенность 1.0, отметка источника «менеджер/продавец» и дата; `ask_seller` помечает поле как ожидающее продавца (карточка → `needs_seller`), следующее решение его закрывает. `card_status` пересчитывается по правилу SPEC 3.4 только по обязательным полям без решения человека. `accept` для поля без предложенного значения — 422.
Почему: SPEC 4.4/4.3: ответ продавца или исправление менеджера → поле решено, карточка пересчитывается.
Обратимо: да.

## 2026-10-16 22:00 · поток C · web (кабинеты)
Вопрос: как показать «ответ получен», если после ответов карточка становится ready и уходит из исключений.
Решение: в таблице исключений статус запроса продавцу: «отправлен» (есть открытые вопросы), «прочитан» (продавец открыл `/seller/questions`, таблица `seller_reads`), «ответ получен · дата» (все вопросы закрыты, но карточка осталась в исключениях); плюс блок «Ответы продавцов» на `/manager` (последние 8 ответов с датой) и отметка на странице карточки. Вопросы продавцу показываются только по обязательным полям (conflict/missing) и по полям, которые менеджер явно отправил продавцу. Индикатор «попадёт в N из M фильтров»: M — число обязательных полей схемы, N — сколько из них заполнено (предзаполнение или ввод продавца); кликов нет, поэтому без веса по трафику. Значение, которое продавец изменил в форме перед «Сохранить», записывается как `seller_answer`; предложенное и не изменённое — не считается подтверждённым. Правка существующей карточки продавцом не реализована (только создание).
Почему: самое дешёвое решение, покрывающее критерии SPEC 4.5.
Обратимо: да.

## 2026-10-16 22:00 · поток C · /v1/feedback, /v1/queue
Вопрос: HTMX шлёт form-encoded, контракт API — JSON.
Решение: `POST /v1/feedback` принимает и JSON, и форму; при заголовке `HX-Request` возвращает HTML-фрагмент (поле формы `view` выбирает фрагмент), иначе JSON `{ok, feedback, card_status}`. `GET /v1/queue` — список карточек с `category == "unknown"`; черновики схем отдельно в `/manager/categories`. `POST /v1/categories/{id}/approve`: `<id>.draft.yaml` → `<id>.yaml` (существующий файл заменяется), id только `[A-Za-z0-9_]`, нет черновика — 404.
Почему: HTMX без доп. расширений; одна точка записи разметки.
Обратимо: да.
